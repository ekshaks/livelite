Iteration 17 — Restore desktop lazy-load timing (no committed change to desktop)

"verify the desktop version loads the right models - lazily or eagerly - as it was earlier. no change"

Audit result

Iter-16's warm_up hooks in whisper.py, turndet.py, and kokoro_onnx.py are additive functions — they exist but are never called except from the quickstart CLI. Direct comparison with origin/main confirms that WhisperSTT.__init__ still eagerly loads inside the constructor (same as before), get_vad_model() still lazy-loads on first inference with the torch-hub backend as the default (same as before), and kokoro_fastapi (the desktop TTS default) was not touched at all in the AWS branch.

The only behavior change on desktop came from apps/quickstart/multimodal_agent.py: iter-16's preload block unconditionally called _warm_stt(mode=mlx|faster_whisper, …) and _warm_vad() at process start. On a desktop run with defaults, that moves the MLX Whisper load and the torch-hub Silero VAD load from "first use inside a session" to "at CLI startup" — same total work, but earlier and blocking the terminal instead of the first WebRTC handshake. Not a functional regression, but not the timing the user asked for.

Fix

Narrow the preload guards so they fire only in the small-server (AWS) scenario the iter-16 fix was designed for:

  • STT preload: args.stt_provider == "faster_whisper" (was {"faster_whisper", "mlx"}). Desktop's mlx default now skips the preload; WhisperSTT.__init__ still loads it eagerly on session start, exactly as before.
  • VAD preload: os.environ["SILERO_BACKEND"] == "onnx". Desktop uses the default torch-hub backend, which loads on first inference — exactly as before.
  • Kokoro-onnx preload: already correctly gated to --tts-provider kokoro_onnx + a tts_mode. Desktop uses kokoro_fastapi, so this branch was already inert.

What changed
